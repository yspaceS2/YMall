# YMall 기술적 회고

## 해결하려 한 문제

YMall은 화면 수보다 커머스에서 실패하기 쉬운 경계를 설계하고 검증하는 데 초점을 맞췄습니다. 주문·결제 상태 일관성, 역할별 소유권, 비동기 이벤트 재처리와 운영 관측 가능성을 핵심 문제로 다뤘습니다.

## 효과적이었던 선택

- **도메인 중심 모듈형 모놀리스**: 분산 배포 복잡도를 늘리지 않으면서 회원, 상품, 주문, 결제와 정산의 책임을 분리했습니다.
- **Transactional Outbox**: 주문 저장과 Kafka 발행 사이의 이중 쓰기 문제를 완화하고 발행 실패를 추적할 수 있게 했습니다.
- **결제 서버 검증**: Frontend Callback을 신뢰하지 않고 소유자, 금액, 상태와 공급자 결과를 Backend에서 검증했습니다.
- **자동 품질 기준**: Backend·Frontend·E2E·API 계약·Secret Scan을 PR 검증에 포함하고 k6와 모니터링으로 성능을 재현했습니다.
- **제한된 자원에서의 AI 비동기 처리**: 리뷰 저장과 모델 추론을 Kafka로 분리하고 동시 추론을 제한해 운영 서버의 응답성과 AI 기능을 함께 유지했습니다.
- **수동 승인형 CD**: CI는 변경마다 자동 검증하되 운영 반영 시점은 직접 선택하고, 이후 배포·헬스체크·롤백·Slack 알림은 자동화했습니다.

## 확인한 한계

- 단일 OCI 인스턴스는 배포와 운영을 직접 경험하기에는 적합하지만 고가용성이나 인스턴스 장애 격리까지 보장하지는 않습니다.
- Kafka와 Outbox는 장애 대응력을 높이는 만큼 재시도, DLT와 복구 절차를 계속 관리해야 합니다.
- 기능과 문서가 함께 늘면서 문서가 코드보다 뒤처질 수 있어 README는 전체 지도, 세부 문서는 한 책임을 갖도록 재구성했습니다.
- AI 리뷰 요약은 운영 환경에서 실제 생성 흐름을 검증했지만 상품군이 늘어나면 품질·지연과 서버 자원 사용을 다시 평가해야 합니다.
- Frontend 테스트 커버리지는 측정 체계를 마련했지만 인증·결제·역할별 실패 흐름을 중심으로 추가 보강이 필요합니다.

## 다음 개선 과제

| 우선순위 | 과제 | 완료 기준 |
| --- | --- | --- |
| 높음 | Frontend 위험 기반 테스트 확대 | 인증·결제·권한 실패 흐름을 우선 보호 |
| 중간 | 관측 알림 기준 | 오류율·지연·Consumer Lag·DLT 임계치와 대응 연결 |

| 낮음 | AI 품질 회귀 평가 | 상품군별 요약 품질·안전성·지연 기준 자동 비교 |

## 운영까지 진행하며 배운 점

로컬 DB를 운영 환경에 복원한 뒤 상품 이미지가 보이지 않는 문제를 통해 DB의 파일 경로와 실제 업로드 볼륨을 하나의 복구 단위로 봐야 한다는 점을 확인했습니다. 이후 DB dump, 업로드 압축 파일과 체크섬을 같은 백업 세트로 만들고 임시 DB 복원 검증 절차를 추가했습니다.

AI 모델도 기능 구현만으로 끝나지 않았습니다. 제한된 OCI CPU와 메모리에서 사용자 요청과 추론을 분리하고, 기존 요약 제공과 동시 추론 제한을 적용해야 실제 서비스와 함께 실행할 수 있었습니다. 새로운 기술을 완전히 이해한 뒤 시작하기보다 실제 문제에 적용하고 실패를 확인하는 과정이 학습에 도움이 됐지만, AI가 구현 속도를 높여도 검증과 기술부채에 대한 책임은 개발자에게 남는다는 점도 배웠습니다.

## 문서와 주석 원칙

구현 완료, 배포 후 확인, 향후 아이디어를 같은 상태로 표현하지 않습니다. 코드 주석은 동작을 번역하지 않고 외부 계약, 도메인 정책, 보안·멱등성처럼 코드만으로 이유가 드러나지 않는 부분에 선택적으로 추가합니다.
